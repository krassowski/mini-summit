The AI follows written instructions, so first drafts have the structure that the playground expects.

The same commands as you

The AI runs JupyterLab commands: create, load, export, share.

We sent four improvements to jupyterlite/ai. Next: code completion and error checking (LSP) in JupyterLite.

Why jupyterlite/ai and not jupyter-ai: it needs no server, so the same AI works in JupyterLite.

Tool calls map to the same JupyterLab commands as the buttons. AI actions and manual actions take the same path, which makes them easy to debug.

Lint

Agents can skip AGENTS.md.
They cannot skip a lint error.

AGENTS.md
  • 68% of instructions followed when there are 500 of them
  • +20% cost, and no better results in general
  • When an agent skips a line, nothing fails

Sometimes followed, and no error when it is not

A lint rule
ui-tests/tests/run-cell.spec.ts
  12:3  error  Use page.notebook.setCell() / runCell()
               instead of raw cell selectors
               jupyter/galata-prefer-notebook-cell-helper

Runs every time. Names the file, the line and the fix.

The agent does not need to know the rule. The linter tells it.

Models are good at code they have seen often. Galata helpers and Lumino signals are a thin slice of the internet.

AGENTS.md helps, but: with 500 instructions the best model followed 68% (IFScale). Context files raised cost by over 20% without improving success in general (Evaluating AGENTS.md, 2026). And when a line is skipped, nothing fails.

(Click) A lint rule runs every time and the error names the fix. Agents are very good at reading an error and acting on it.

From Darshan's OpenTeams post "Your AI Agent Ignored AGENTS.md. Your Linter Won't Let It."

prototypelintbuildtest
Lint · reusable

When should you write a custom lint rule?

  1. 1TypeScript cannot check the convention
  2. 2It is rare in public code, so models have not learned it
  3. 3Breaking it causes no error
  4. 4The error message can say what to do instead

Wrote the same review comment three times? That comment is your rule.

AGENTS.md
## Before you finish
- Run `jlpm eslint` and fix every
  `jupyter/*` error.

Four conditions for a rule worth writing. If you typed the same review comment three times, you have the spec.

Agents are good at writing ESLint rules, because rule APIs are common in public code even when your conventions are not.

Keep AGENTS.md, but give it one job: point at the linter.

Led by Darshan Paudyal (OpenTeams). Started in GSoC 2024 by Ronan Coutinho, mentored by Frédéric Collonval.

Darshan led this one too. Before: to build an extension you installed all of JupyterLab, because the build tooling lived in the JupyterLab repository.

That hurt Linux packagers (a circular dependency), and extension authors whose build changed with every JupyterLab upgrade.

(Click) Now: jupyter-builder on PyPI and npm. Compatibility is checked against published metadata, so no JupyterLab install. It is backwards compatible with @jupyterlab/builder.

Build

A fix in 24 hours, without a JupyterLab release

Rspack 2.0

The new bundler switched to Module Federation v2 by accident.

Report

Extensions that use older shared packages break. The jupyter-chat maintainers report it.

Under 24 hours

A jupyter-builder minor release goes back to Module Federation v1.

For everyone else

No JupyterLab release needed. Extensions upgrade when they are ready.

The build system now has its own releases.

A real story from the August report. Rspack 2.0 switched to Module Federation v2, which changed how shared package versions are matched. Extensions depending on older non-singleton packages broke.

Before jupyter-builder this needed a JupyterLab release and a long discussion. Now a builder release fixed it within 24 hours of the report.

Feedback also came from developers at UC Berkeley, the Space Telescope Science Institute, jupytergis and jupyter-chat.

Agents need fast and reliable tests

55 min per run8
15 min per run30
rounds of change and check in a working day
  • A failure on your laptop is a real failure. No retries hide flaky tests, so agents stop adding fixed waits.
  • The rules are in files that agents read: AGENTS.md, the contributing guide, lint rules.
  • Every new or changed test has a video in the report.

28 of 30 recent PRs that changed a UI test were AI-assisted. A developer with an agent needs a test that runs on their machine, a result they can trust, and an answer in minutes.

At 55 minutes per run a working day has room for about 8 rounds; at 15 minutes, about 30.

Given a false failure, an agent reruns tests or changes code that was not broken, often by adding a fixed wait.

Part 3

New challenges with AI, and our answers

ChallengeWhat we do
Code arrives faster than people can review itMove feedback from people to tools: lint, badges, snapshot PRs on request
Agents skip written conventionsLint rules whose error message says how to fix it
Flaky tests mislead agentsTests that give the same result on a laptop; a weekly report of flaky tests
More first-time contributorsWorkflows that need no maintainer; an AI usage question in the PR template
Bots that act on forks can be abusedNo write access in jobs that read fork content; maintainer approval; zizmor checks

Five challenges, each with a response that is already in place.

Review time is the scarce resource. Every check a tool can make is a review comment a person does not have to write.

The PR template asks whether AI generated some of the content; that is where the 28 of 30 number comes from.

Open work: 2.4 flaky tests per run remain, 36 fixed waits are still behind disable comments, and the playground's LSP in JupyterLite waits on upstream releases.
